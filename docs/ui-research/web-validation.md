# 取引履歴の Web 実行検証

2026年11月22日。main の `daf9d53` とこのブランチの Expo Web 本番エクスポートを、同じ Linux Chromium 上で操作した。通常幅で最初に読める明細数を保ち、小画面で大きい金額が切れる問題を解消できた。大量データでは最初に描画する行数が大幅に減った。一方、初回表示から一気に一覧の最下部へ移動する操作は、可変行高を順に測定するため遅い。

## 条件

|項目|実行内容|
|---|---|
|ビルド|Expo 58.0.26、Expo Router 58.0.32、React Native 0.88.1、React Native Web 0.21.4。両方とも `expo export --platform web` の静的配布物|
|ブラウザ|Playwright 1.63.0、Linux Chromium 156.0.8078.79。日本語、各ケースは個別のプロファイル。仮想的な表示領域は 360×799、393×872、600×960 CSS px|
|データ|同梱の `history-fixture.mjs` の架空明細。2026年11月、0・5・50・1,000・10,000件を同じ月に置く。旧形式から実際の IndexedDB ストアへ読み込ませた。端末の日付のみ11月22日で固定|
|追加条件|360 幅で文字と明示的な行高を 150% にし、最初の支出を ¥9,876,543,210 に変更した場合、収入のみを除いた場合、最後の1件のみを10月に置いた場合も実行。いずれも一時プロファイルのみ|
|監査|393 幅・5件の明暗で axe-core 4.10.3 を文書全体に実行。WCAG 2 A/AA、2.1 AA、2.2 AA タグを使用。Tab、Enter、長押し、戻るは別途操作した|

## 大量明細

「初期」はホームの取引タブを押して先頭行が描画されたとき、「末尾」は表示が安定した後。行数は画面外を含む実 DOM 内の明細タイトル数で、隣月のプレビューを除外した。DOM 全要素数はページ全体を数えた。

|同月件数|初期の明細行 main → 候補|初期の DOM 要素 main → 候補|末尾の明細行 main → 候補|末尾から開けた正しい ID|
|---:|---:|---:|---:|---|
|50|50 → 5|769 → 325|50 → 38|`preview-37`|
|1,000|1,000 → 5|8,369 → 325|1,000 → 46|`preview-987`|
|10,000|10,000 → 5|80,369 → 325|10,000 → 46|`preview-9993`|

1,000件と10,000件は追加で3回ずつ main→候補の順に直列実行した。下表は3回の中央値（括弧内は最小～最大）。「先頭表示」はホームで取引を押してから、見出し・検索ボタンとパン店の行を Playwright が検出するまで。遷移アニメーションや待機処理を含む。

|単月件数|先頭表示 main → 候補、ms|ホイール中の RAF 間隔 p95 の中央値 main → 候補、ms|
|---:|---|---|
|1,000|1,074（952～1,127）→ 627（566～820）|23（23～26）→ 22（18～32）|
|10,000|7,473（7,196～8,063）→ 409（401～435）|137（128～140）→ 20（20～23）|

1,000件のホイール測定値には両実装で重なりがある。10,000件では全3回で候補の先頭が早く、ホイール入力中の RAF 間隔も短かった。5件の通常画面ではこの改善幅を前提にできない。

650 px のホイール入力で既存行以外が実際に表示されることを確認し、185 px のホイール入力10回を加え、その間の `requestAnimationFrame` 間隔を 1.5 秒採った。一覧の末尾へは 65 ms ごとにスクロール可能な最終位置へ飛んだ。最後の日付が現れて高さが10回安定するまで繰り返し、最古の行を開き、戻って同じオフセットも検査した。候補の1万件はこの最深部移動に約1分を要した。変動する行高の未計測部分を段階的に展開するため、スクロールバーで遠端に瞬時に移動したい場合は改善余地がある。行高が変わる長文・メモ・大文字に一定高を仮定すると、途中の明細へ誤って着地する。

同じ1万件で日付が分かっていれば、右上のカレンダー → 11月1日を選ぶと、その日だけの526件が665 msで表示された。先頭の「商店街で買い物」を押して正しい取引 `preview-18` を開くまで、カレンダーを押してから813 ms。日別表示に戻って End キーを押し、最終行「帰りのバス」から月の最古の行 `preview-9993` も開けた。店名が分かる場合は右上の検索 → 「青葉」と入力 → 「青葉ベーカリー」を選ぶと `preview-0` を開けた（自動入力・操作込み797 ms）。これらは最終 Web 版の各1回の実測。カレンダーの日別表示はその日の全件を描画する。

## 再現

両リビジョンで依存関係を解決し、それぞれの `apps/mobile` で本番 Web 配布物を別々のフォルダに出力する。以下は候補の例。ブラウザ実行は、この文書と同じツリーのリポジトリルートから行う。Chromium のパスを省略すると Playwright の既定ブラウザを使う。axe を再実行する場合は `AXE_PATH` に axe-core 4.10.3 の `axe.min.js` を指定する。

```sh
# apps/mobile で実行
EXPO_NO_TELEMETRY=1 CI=1 node node_modules/expo/bin/cli export \
  --platform web --output-dir /tmp/mane-history-web --max-workers 2

# リポジトリルートで実行。出力はリポジトリ外。
CHROMIUM_PATH=/usr/bin/chromium \
AXE_PATH=/tmp/axe-core/package/axe.min.js \
node docs/ui-research/history-web-check.mjs \
  /tmp/mane-history-web /tmp/mane-history-results candidate
```

`FIXTURE_DIR` に各件数の JSON があればそれを使い、省略時は同梱ジェネレーターで同じ内容を作る。結果はラベル別 JSON と PNG。 `CASE_FILTER='5-393-light'` は該当画面と障害復帰・月遷移、`WHEEL_SAMPLE_ONLY=1` は50件以上のホイール測定、`DEEP_PATHS_ONLY=1` は1万件の日付・店名からのアクセスを再検証する。ブラウザの CSS px、RAF 間隔、Playwright の待ちを含む時刻には、ネイティブ GPU のフレーム時間・Android 実機の処理時間という意味はない。
