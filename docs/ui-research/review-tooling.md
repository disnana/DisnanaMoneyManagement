# 設計ツールを取引履歴の設計と検証に使う条件

2026年11月22日調査。指定された13 URLのうち、12件は発行元ページの本文を確認した。Stitch のサービス画面（B02）は公開 HTML のメタ情報まで確認し、機能は別の Google 公式記事で裏づけた。Figma のヘルプと開発者サイトは直接の HTTP 接続が 403 だったため、ウェブ閲覧ツール経由で指定 URL の原文を読んだ。以下の日付は発表記事の公開日。ヘルプ・開発者資料は参照時の公開版で、個々の改訂日は本文から特定できていない。

このブランチで使うのは、同じ取引データでレイアウト案を比較する方法、コンポーネントの可変部分の記述法、検証の単位である。Stitch での生成、Make ファイルの作成や公開、個別の Figma デザインの読み取り、Code Connect の公開は行っていない。

## Stitch

### B01　候補を比較する軸を一つに絞る

2025年5月20日の発表では、テキストに加えて手描きのワイヤーフレームを入力でき、生成した複数案をチャットで直し、Figma へ貼り付けたりフロントエンドコードを書き出せる。履歴で比較したいのは「1件目をすぐ見つけられるか」。月・家計グループ・取引・文字サイズを固定し、月次収支を大きく見せる案と、収支を一段にまとめて日別明細を繰り上げる案で、最初の画面に読める件数とフィルタまでの操作数を比べる。候補ごとに色・件数・金額まで変えると、配置の効果を判断できない。記事で紹介された出力には Android の戻る、読み上げ、リスト仮想化の保証がないので、それぞれ Expo で試験する。[Google Developers Blog](https://developers.googleblog.com/en/stitch-a-new-way-to-design-uis/)

### B02　別の画面へ持ち越せるのは設計の規則

指定 URL は `stitch.google.com` へ転送され、説明メタにモバイル・ウェブ用 UI の生成とある。実行後の編集画面は未確認。2026年4月21日の別の公式記事では、設計規則を持ち運ぶ `DESIGN.md` 草案に色の用途を記述できる。5月19日の記事では、既存のデザインやコードを渡し、キャンバスで途中経過を見ながら修正できる。今回なら「背景、日付見出し、タップ可能な行、選択中」の役割を既存テーマの `bg`、`textSecondary`、`text`、`tint` と照合し、意味・明暗・文字での区別を設計文書に残す。データを伴う実画面を外部に送らず同じ判断を Expo の実装に適用できる。草案の公開は生成画像・コードの利用許諾やアカウントの価格を示さない。いずれも今回未検証。[サービス](https://stitch.withgoogle.com/) · [設計規則の草案](https://blog.google/innovation-and-ai/models-and-research/google-labs/stitch-design-md/) · [2026年の機能更新](https://blog.google/innovation-and-ai/models-and-research/google-labs/stitch-updates/)

## Figma Make

### B03　既存のフレームから遷移を試す

2025年5月7日の発表では、Design のフレームを構造・メタデータごと Make へ渡せる。要素を指して操作時の振る舞いを変更できる。履歴なら仮の取引をタップして編集し、キャンセルして同じ検索条件に戻れるところまでを一続きの試験にする。静止画だけでは、戻る際に条件やスクロール位置を失う不具合を見落とす。記事当時の生成モデル名は現在の構成・契約の根拠にしない。[Figma 発表記事](https://www.figma.com/ja-jp/blog/introducing-figma-make/)

### B04　プレビューと差分を両方見る

公開ヘルプには既存フレームの添付、要素を指定した編集、ブラウザでの操作、Files でのコード編集、Review での差分確認がある。履歴を 0 件にした際、日付・フィルタが操作可能かをプレビューで確認し、変更差分では保存処理・月次計算への編集の有無を確認する。試作時も第三者のフォント・画像・パッケージの権利確認は作成者側にあるため、アプリに入れる素材は既存資産を起点にする。公開出力の形はウェブサイトなので、ここでの動作確認と Android/iOS 上の検証をそれぞれ記録する。[Explore Figma Make](https://help.figma.com/hc/en-us/articles/31304412302231-Explore-Figma-Make)

### B05　草案を誰に見せられるかを先に決める

FAQ の権限表では、有料プランの Full シートはチーム内作成・共有・公開に対応し、Dev・Collab・View でも下書きで試せる。Starter はチームライブラリをスタイルの文脈に使えず、ウェブへの公開には Community への公開も必要。組織ごとに AI・公開の管理設定もある。社内の既存 UI キットを前提とする案は権限が合うときだけ有効。今回はテスト用の明細、ブランチ、チャット内の比較画像で、テスターと同じ状態を共有する。席・AI クレジット残量・実際の契約料金は参照していない。[Figma Make FAQ](https://help.figma.com/hc/en-us/articles/31722591905559-Figma-Make-FAQs)

### B06　直したい条件を一つの要素に結び付ける

公式ワークフローは、複雑な画面をフレーム単位で渡し、配置の確定後に動作を加え、選択範囲や注釈で修正箇所を指示する。スクリーンショットから正確な色値を抽出する用途には限界があり、小さいモバイル画面への出力も改善中と明記している。実装の受け入れ条件は、例えば「狭い幅で長い店名とポイント控除が同時に出ても、金額の符号と桁が読める」「編集を閉じると履歴に戻る」のように一度に確認できる形にする。再現には架空の取引を使う。Make に実データ・鍵を投入する必要はない。[Create a Figma Make file](https://help.figma.com/hc/en-us/articles/31304485164695-Create-a-Figma-Make-file)

## Figma MCP とコンポーネント

### B07　読み取れる設計情報と端末で確かめる情報

MCP は選択フレームからレイアウト・コンポーネント・変数を取得し、Make のリソースや Code Connect の対応も取得できる。キャンバスへの書き戻しはリモートサーバーを必要とし、下書き外への書き込みには Full シートが必要とされる。仮にフレームがあれば、フィルタの選択色、余白、文字の優先順位を変数と照合する。日本語の読み上げ順、物理戻る、端末上のフレーム時間はネイティブ実行で確認する。今回は対象 Figma ノードの指定がなく、個別ファイル由来のトークンや寸法として扱える情報はない。[MCP の公式概要](https://developers.figma.com/docs/figma-mcp-server/)

### B08　接続の存在とデザインへのアクセス権を区別する

公式リモートエンドポイントは `https://mcp.figma.com/mcp`。Codex アプリではプラグインから許可し、CLI では `codex mcp add figma --url https://mcp.figma.com/mcp` の後に Figma 側のサインイン・承認が入る。CLI のエンドポイント登録だけではスキルも入らない。今後対象フレームを使うときは共有されたノードとアクセス権を確認し、取得できた変数と実装上の対応を記録する。認証・接続失敗は設計データ未取得として残し、今回のようにリポジトリの `theme` と端末のレンダリングを調査元として明示できる。[リモートサーバーの設定](https://developers.figma.com/docs/figma-mcp-server/remote-server-installation/)

### B09　配置が崩れる条件を設計データに含める

指針は、繰り返す単位のコンポーネント化、色・余白・角・文字への変数付与、意味での命名、Auto Layout によるリサイズ試験、静止画に現れない動作への注釈を挙げる。取引履歴では「日付と日計」「取引内容と口座」「金額」「任意のメモ・ポイント充当」が自然な単位。店名列は伸縮し、大きな文字で同じ行に収まらないときは金額を独立させる。符号、振替先、支払額を削って幅を合わせない。短い通常行だけで決めず、小型端末・拡大文字・長い日本語を同時に入れて幅を変える。既存 `TxRow` の内容と金額整形、OS 別 `usePalette` が実装側の照合先。[ファイルの構造化](https://developers.figma.com/docs/figma-mcp-server/structure-figma-file/)

### B10　デザイン上の「支出」をコードの値に結び付ける

MCP は接続済みコンポーネントについて、バリアント値、import、利用例、個別指示を文脈に含められる。CLI 接続では props の明示的な対応を詳しく書ける。UI 接続は最小の利用例に向く。資料の対象は Professional・Organization・Government・Enterprise の Full または Dev シートで、Professional で返る接続は有効なライブラリとフレームワークに限られる。実装の候補は `Segmented` の表示名「支出」と ID `expense`、`TxRow` の `showMemo`、`HeaderAction` の `label/selected/disabled`。同じ外観の押下先や読み上げ名は用途ごとに別設定が必要で、見た目だけを props に対応づけると不足する。今回はこの対応をコードで確認し、外部への登録はしていない。[Code Connect と MCP](https://developers.figma.com/docs/figma-mcp-server/code-connect-integration/)

### B11　React Native のサンプルを実際の props に合わせる

指定ページは React/React Native を対象にした旧パーサーのガイドで、現行の保守対象を template files と明記する。旧ガイドのスニペットは文字列として処理され、条件式を実行した表示例にはならない。新規で接続する場合は `.figma.ts` または `.figma.js` を対象に設定し、ノードの URL と実際の import を指定する。例えば `TxRow` は `amount`・`type` を個別に受け取らず `tx` を受けるため、合成の取引オブジェクトを渡す利用例から作る。本番の集計をテンプレートに複製すると本体の変更に追従できない。対象ノードと運用担当が決まるまでは `*.figma.ts` を追加する利益が小さい。[指定の React ガイド](https://developers.figma.com/docs/code-connect/react/) · [現行のテンプレート仕様](https://developers.figma.com/docs/code-connect/template-files/) · [移行の仕様](https://developers.figma.com/docs/code-connect/templates-migration-guide/)

## モデル選定

### F01　設計レビューと機械的な修正の評価を分ける

API 向けガイドは、設計上の難しい判断や複雑な解析に GPT-6.2 Astra、既存コードへの変更やテストには GPT-6.2 Sol を候補に挙げる。API の通常作業では Sol の medium が出発点。ここで評価すべき設計判断は「カレンダーから戻れるか」「ポイント充当後の実支払と元の取引額を見分けられるか」。反復修正は、同じ入力・初期設定で失敗した例を再実行して評価できる。公式自体が製品・版による利用条件の違いを示しており、推奨モデルは家計簿アプリの性能指標や採用フレームワークの根拠にはならない。[OpenAI Model selection](https://developers.openai.com/api/docs/guides/model-selection)

### F02　比較を再開できる形で証拠を残す

ChatGPT Work/Codex 向け資料は推論量と所要時間・使用量の関係を説明する。参照時の Codex の標準文脈は 6.2 Astra が 272,000、6.2 Sol が 500,000 トークンで、両方に個別の拡張設定がある。60件を一括読込したという主張の代わりに、各資料の対象版・アクセス結果・採否・再試験条件を出典 ID とともに保存すれば、設計判断を少量の文脈からでも再現できる。この資料で確認できたのは製品の公開説明。契約ごとの枠・課金額や今回の実行モデル間の優劣は測定していない。[ChatGPT Work/Codex の Models](https://learn.chatgpt.com/docs/models)
