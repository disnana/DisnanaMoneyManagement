# モバイルUI設計・実装・検証ノート（Codex用・詳細版）

対象: 日本語の家計簿/資産管理/レシート解析を備えるAndroid/iOSアプリ。2025〜2026年のUIツールと公式技術資料を検討した上での実用設計指針。特定アプリのスクリーンショットが手元にないため、画面の実測値や現状の品質は推定しない。**以下の数字は指定がない限り設計初期値/検証候補であり、DMMの社内実装値ではない。**

---

## 1. デザインの目的を「綺麗」に限定しない

「DMM系の完成度」を抽象形容詞としてAIに伝えるだけだと、余白の広いカード型ダッシュボードや派手なアニメーションに逃げやすい。目的を操作と情報で定義する。

| 評価対象 | 成功の判断 | 避けるべき実装 |
|---|---|---|
| 情報の優先順位 | 開いた瞬間に今月の支出/利用可能額/直近の取引が識別できる | 大きな挨拶、装飾バナー、無意味なKPIの羅列 |
| 記録の速さ | 金額、日付、カテゴリ、口座を迷わず登録できる | 階層深いメニュー、登録後の所在が不明 |
| 把握の速さ | 月切替、内訳、予算超過の理由が理解できる | 円グラフのみ、凡例だけでカテゴリ判断 |
| 一貫性 | 同じ処理は同じ見た目/位置/反応 | 同名ボタンで違う動作、画面ごとに異なる余白 |
| 安心感 | 保存成否、取り消し、読み込み、競合が明確 | タップ後の沈黙、誤操作の即時確定、偽の完了表示 |
| 性能 | スクロール・キーボード・画面遷移が安定 | 全件レンダリング、毎フレーム重い計算 |
| アクセシビリティ | 大文字/読み上げ/弱い視力でも利用可能 | 小さすぎる文字、色だけの収支区別 |

設計の優先度は **正確さ > 操作性 > 視認性 > 一貫性 > 心地よい動き > 装飾** を基本とする。金融情報を扱う場合、派手さより誤操作防止を優先。

## 2. まず現行画面を監査する：画面一覧と現状把握の方法

Codexに、コードだけではなく**実機スクリーンショット**を取得させる。現在の画面が魅力的でも、すべて消してゼロから作り直す前提にしない。

監査対象の候補:

1. 初期表示（ログイン状態/未ログイン/データ空）
2. ホーム（今月収支、予算、直近履歴、クイックアクション）
3. 取引履歴（月切替/日別グループ/検索/フィルタ/編集）
4. 取引追加（支出/収入/振替、金額、日付、口座、カテゴリ、メモ）
5. 口座/カード/資産の一覧と明細
6. 分析（カテゴリ内訳、月別推移、予算との差）
7. レシート解析（撮影/取込、解析中、候補修正、一括/商品別保存）
8. 設定（外観、データ入出力、AIクレジット、連携、通知）
9. 入出力エラー、許可拒否、オフライン、同期中

画面ごとに次の表の形式で記録すること。

```text
Screen ID:
User goal:
Primary action:
Secondary action:
Critical information:
First glance order: [1, 2, 3 ...]
No. of taps for primary task:
Existing strengths:
Problems (reproducible observations only):
Screenshot reference, device, dimensions, font scale, theme:
Known accessibility issues:
State variants: ideal / empty / loading / error / partial / offline
Proposed small correction:
Possible regression:
Validation:
```

この段階では「なんとなく古い」「Materialに反するから悪い」といった感覚で機能を削らない。利用状況・用途に基づいて判断する。

## 3. DMM Turtleから何を学ぶべきか

Turtleの重要な点は、DMMアプリの角丸や色をコピーすることではなく**判断を共通化して、画面が増えても品質が崩れないこと**。

### 3.1 原則を決定ルールに落とす

- Achieve Goals: 主要操作は迷わず完了できる。最小タップ数だけでなく認知負荷と誤操作リスクも確認。
- Bring out Abilities: 画面ごとに同じ部品を再実装せず、開発者が本質的な機能に時間を使える。
- Consistency: 色・余白だけでなくprops、キーボード、戻る操作、状態表示まで揃える。
- Design Intent: なぜそう配置したかを残し、後から変更理由を追える。
- Evolve: A/Bやユーザーテストで改善可能な構成とする。

### 3.2 Figmaからコードを生成する際の具体策

- Frame1268 / Group5のような名前を使わず、`Home / MonthlySummary / BudgetProgress / TransactionList / TransactionRow`のように役割で命名。
- Auto Layout、Fill、Max width、変数・コンポーネントを使う。座標の絶対指定を最小化。
- テキストの最小/最大長、折り返し、金額が数桁伸びたときの挙動、負数の見た目を注釈として残す。
- バリアントのラベル（default/pressed/disabled/loading/error/selected）をコードのpropsに対応付ける。
- Figmaの表現と実装のAPIを対応させる。例: `Button { variant: primary | secondary | text, size: sm | md | lg, loading: boolean, fullWidth: boolean }`。
- AIが毎回色コードや幅を推測しないよう、トークンまたはpropsを優先する。
- Web固有のHTMLツリー/タグ指示は、React Native/Compose/Flutterへ適切に読み替える。プラットフォーム固有のアクセシビリティセマンティクスを失わない。

### 3.3 公開資料の限界

2026-11-22時点、Turtleの公式サイトはFigma UI Kitへのリンクを示すが、デザイントークン詳細カタログ、コンポーネントの詳細ページ、公開GitHub、Storybookは準備中の項目がある。**Codexは公開資料にないpropsやパッケージ名を創作しないこと。**

## 4. UIに必要なデザイントークンの設計例

色の実値はブランド原案とコントラスト試験で決める。下記は**名前と階層**の例で、色指定の完成案ではない。

```ts
// theme/tokens.ts : 例。既存のテーマ構成に合わせて統合する。
export const space = {
  xxs: 2, xs: 4, sm: 8, md: 12, lg: 16, xl: 20,
  xxl: 24, xxxl: 32, section: 40,
} as const;
export const radius = {
  none: 0, xs: 4, sm: 8, md: 12, lg: 16, xl: 20, pill: 999,
} as const;
export const control = {
  minTouchTarget: 48,
  rowMinHeight: 52,
  iconSmall: 18,
  iconRegular: 24,
} as const;
export const typeRole = {
  heroAmount: { fontSize: 30, lineHeight: 38, fontWeight: '700' },
  sectionTitle: { fontSize: 18, lineHeight: 26, fontWeight: '600' },
  body: { fontSize: 15, lineHeight: 23, fontWeight: '400' },
  supporting: { fontSize: 13, lineHeight: 19, fontWeight: '400' },
  footnote: { fontSize: 12, lineHeight: 17, fontWeight: '400' },
} as const;
```

設計の注意:

- 余白は4dpの倍数だけに厳密固定する必要はないが、恣意的な`13px`, `19px`の増殖を防ぐ。まず4/8/12/16/24/32の小さな集合。
- Androidの物理pxではなくdp/論理ピクセルを扱う。フォントはユーザーのスケーリングを無視しない。
- ライト/ダークを別CSS群としてハードコーディングせず、意味のある色名にする。
- `surface`, `surfaceRaised`, `textPrimary`, `textSecondary`, `divider`, `interactivePrimary`, `success`, `warning`, `danger`, `income`, `expense` 等、機能に対応した意味のある色ロールを使う。
- `income=緑`, `expense=赤`など色だけに依存せず、符号、文脈、ラベルも併用。
- ダークテーマは単純なRGB反転にしない。OLEDで真っ黒にするか濃いsurfaceにするか、読みやすさと状態の区別で検証。
- モノスペース/桁揃えの数値表示を検討。フォントが対応する場合はtabular figuresを利用。`¥500,000` など桁数で列が踊らないか見る。
- 高さ52や文字15は初期の設計値。高齢者/大文字設定での再評価が必要。

### 4.1 トークン・コード・Figmaの単一ソース方針

- 既存のthemeファイルがあるなら再利用し、二重管理を避ける。
- 新規にFigma Variablesを作るなら、名前とlight/darkモードの構造を揃える。
- Token→実装の自動生成は有効だが、採用するならビルド/型チェックで同期を検証。
- トークンを更新するとどの画面が影響するかがわかるようにする。

## 5. 「カードだらけ」を避けた視覚階層

情報が多いアプリに、すべての情報を丸いカードで囲うことは逆効果になり得る。カードと背景は用途によって選ぶ。

| UIの種類 | 推奨される表現候補 | 理由 |
|---|---|---|
| 月の支出/収支のトップ情報 | 画面背景に統合して大きな数値と短い補助文 | 目が最初に到達する場所。装飾を減らす |
| 予算の進捗 | 細いバー+金額/割合/残額 | グラフだけでは意味が分かりにくい |
| 取引履歴 | 余白 + 仕切り線 + 日付見出し | 情報密度が高く、繰り返し閲覧しやすい |
| 達成・警告・操作促進 | 控えめなサーフェス、必要時のみカード | 通常情報との区別が必要 |
| 入力フォーム | グループ/リスト型、見出しと適切な余白 | Android/iOSの慣れた設定・フォーム体験を活かせる |
| 重要な未完了処理 | 視覚的に独立した通知または行 | 緊急性に応じた表現ができる |

カードを使う条件をルール化する。例えば「独立した操作や重要な状態」「他の一覧から視覚的に切り離す必要がある」場合のみ。影・境界線を多重適用しない。

### 5.1 視線誘導の設計

1. 画面タイトルと現在の期間/対象口座を即認識。
2. 一番重要な数値を読む。
3. 同じ視線の流れで比較指標（前月比/予算差/残高）を認識。
4. 必要なら詳細/取引一覧へ進める。
5. 毎日使う追加操作に到達する。

アイコンだけで何の操作か分からないときは、短いテキストラベルを付ける。ホームの情報量は画面サイズに合わせても、重要情報の表示順は一致させる。

## 6. 画面幅、Insets、キーボード、タップ領域

- スマホの標準幅では下部タブを候補にする。Androidでは通常5タブまでを上限の目安とするが、**Expo Native TabsはAndroidで最大5件の制限**が公式にある。
- 600dp以上では画面幅だけでなく、高さ・横向き・多窓も考慮して1→2ペイン化。大きい画面で横幅100%に巨大ボタンを引き伸ばさない。
- 840dp以上では「左: 一覧 / 右: 詳細」等の分割を検討。余白だけを何倍にも広げない。
- ステータスバー/ジェスチャーナビ領域を背景が通っても、アイコン・テキスト・CTAはInsetで避ける。
- キーボード表示時に保存ボタンと金額入力が隠れない。入力完了、戻る、フォーカス順、スクロールを確認。
- 48x48dp以上の操作領域を確保し、24dpのアイコンでも押せる範囲を広げる。近接する操作の誤タップを確認。
- フォントスケールを1.0だけで済ませず、OS側の拡大設定で表示崩れを確認。
- 日付/金額/取引名の長さが異なる端末幅でも省略や重なりがない。
- 文字・線・背景に必要なコントラストを実測。WCAGを参照するなら基準値と対象サイズを明記する。

### 6.1 物理ピクセルや60Hzの誤解を防ぐ

- DP/論理ピクセルとデバイスの画素密度は別。全端末で同じ物理ピクセル数にしない。
- 60Hzなら1フレーム約16.7ms、120Hzなら約8.3ms。ただしアプリ側が満たすべき実際の予算はOS・レンダリング処理に依存。
- 「120Hzに合わせてアニメーションを増やす」ではなく、操作反応とスクロールの安定性を優先。

## 7. ホーム画面の詳細設計

ホームは情報総覧ではなく、日々の判断と記録を始める場所とする。

### 7.1 必須コンテンツの候補

- 期間選択: 表示中の月が分かり、前月/翌月/今月へ戻れる。
- 主指標: 今月の支出総額。収入/収支/予算残額も扱うが表示の序列を決める。
- 予算の進捗: 数値（例：12万円/18万円）と割合の両方。予算を設定していない場合は別状態にする。
- 最近の取引: 店舗名、カテゴリ/口座、日付、金額。行をタップすると詳細/編集へ。
- 追加ボタン: 手入力/レシート/振替などの入口を絞り、メニューが増えすぎたら整理。
- エラー/同期表示: AI処理やインポートに失敗した情報を曖昧に成功として扱わない。

### 7.2 改善候補のバリエーション

A: Minimal / Integrated：トップ指標を背景と一体にし、一覧は仕切り線だけ。最も軽量。

B: Editorial：数値に余裕を持たせ、説明と補助指標は小さめ。コンテンツの読み順を重視。

C: Expressive：重要アクションと選択状態にMaterial 3 Expressive由来の動きや形を限定的に活用。

Codexは各案で「何を優先したか」「失った利点」「操作回数」「最初の画面に入る情報」を比較。装飾の見た目だけで選ばない。

## 8. 取引履歴画面の詳細設計

- 履歴は単一の長いScrollViewに全取引行を追加しない。件数が増えるなら仮想化したリスト。
- 日付ごとの見出し（例：11月22日 日曜日）、日計/期間合計が必要かを判断。残高や集計が正しいことを優先。
- 取引行は金額を右揃え、店名/内容を主、カテゴリ・口座・時刻を補助に。毎行3〜4行以上のテキストを増やさない。
- 項目名が長い、カテゴリ未分類、メモあり、返品/払い戻し、外貨、振替、マイナス金額、複数口座の状態を含める。
- 取引行タップ→詳細、長押し→補助メニュー、スワイプ削除は誤操作リスクを考え選ぶ。削除できるならUndoまたは確認と復元条件。
- フィルタ条件は選択したことが一目で分かる。画面を戻したら勝手にリセットしない方針を検討。
- データが0件のときは「取引がありません」だけで終わらせず、期間変更/追加導線を示す。

### 8.1 仮想化リストの使い分け

- Expoで軽いデータ: `FlatList`がまず候補。
- 件数が多く、描画負担が現れている: `FlashList` v2を候補にし、New Architecture対応を調べる。v1向け`estimatedItemSize`ノウハウをv2へ無条件転用しない。
- Expo UI native `List`/`List.ForEach`: 公式ページとSkillsで説明が一部異なるため、データ件数別に実装/実機計測し適性を判定。設定画面の項目一覧には高相性でも、数万件取引履歴の第一候補として決め打ちしない。
- すべての実装でStable Key、行部品の軽量化、画像の最適化、フィルタ/集計のキャッシュを検討。

### 8.2 `FlatList`の実装イメージ

```tsx
// 実APIに合わせて型やデータ構造を変更すること。
type Tx = { id: string; title: string; category: string; amountMinor: number };
const TransactionRow = React.memo(function TransactionRow({tx, onOpen}: {tx: Tx; onOpen: (id: string) => void}) {
  return (
    <Pressable
      accessibilityRole="button"
      accessibilityLabel={`${tx.title}、${tx.category}、${tx.amountMinor}円`}
      onPress={() => onOpen(tx.id)}
      style={styles.row}>
      <View style={styles.rowContent}>
        <Text numberOfLines={1} style={styles.primary}>{tx.title}</Text>
        <Text numberOfLines={1} style={styles.secondary}>{tx.category}</Text>
      </View>
      <Text style={styles.amount}>{formatMoney(tx.amountMinor)}</Text>
    </Pressable>
  );
});

const renderItem = ({item}: {item: Tx}) => <TransactionRow tx={item} onOpen={openTransaction} />;
<FlatList
  data={transactions}
  renderItem={renderItem}
  keyExtractor={item => item.id}
  // getItemLayout はすべての行高が本当に同じ時だけ使用
/>;
```

注: 例示用のコード。`openTransaction`はコンポーネント側で用意するコールバック。性能を上げるための`memo`も、プロパティが変化し続ける構成では効きにくい。Profilerで測定する。

## 9. 金額入力と取引登録の詳細設計

- 最初に選ぶべきなのは「1画面フォーム」か「ステップ型」か。頻繁な登録ではタップ数が増えるステップ型を安易に採用しない。
- 金額を主役に置き、テンキーの反応、桁区切り、負数、0円、小数が許容される通貨、貼り付け、全角数字、誤入力時の状態を決める。
- 保存操作は1度で分かり、保存中の二重タップを抑える。ただし表示だけ先に成功にしない。
- カテゴリは毎回巨大な一覧から選ばせず、最近/よく使うものを提示。ただし選択結果が曖昧にならないようにする。
- 過去日付や口座を変更するときは、操作が戻しやすいセレクタを使う。
- iOSとAndroidでPicker/Bottom Sheetを揃えすぎず、プラットフォームの慣習に沿う方が自然な場合がある。
- Androidの戻る操作と画面内閉じる操作が矛盾しない。編集中の未保存データをどう扱うか決める。
- 音/触覚は成功時や重要選択に限定し、毎入力で震わせない。
- 検証できるまで、収支の集計ロジック・通貨金額の計算方式をUI変更と同時に書き換えない。

## 10. レシート解析の設計（AIがあるアプリ固有）

このアプリはレシートの読み取り後に、商品別で記録するか、1枚の支出として記録するかなど複数の目的が考えられる。ユーザーに不要な手順を押し付けない。

### 10.1 画面の流れ

1. 取込元選択（撮影/写真/ファイル）
2. 画像の確認と再撮影
3. 解析中（処理中であること、時間がかかっても操作可能な範囲を明示）
4. 結果プレビュー（店舗、日付、合計、商品候補、消費税等の不確実な部分）
5. 記録モード選択（合計で1件/商品別/選択した品目だけ。必要ならユーザーの既定値を保持）
6. 修正可能なレビュー（認識ミス、カテゴリ・用途の推定、重複、税込/税抜）
7. 確認して保存（重複・保存先・クレジット消費の説明）
8. 保存結果、修正/取り消し/履歴への入口

### 10.2 エラーと信用の設計

- 読み取り精度が不十分な場合に自動で無言確定しない。
- 解析に失敗した場合は、課金・クレジット消費の成否も含めて説明を揃える。残高や請求の事実はバックエンドに確認する。
- AIの推定値とレシートから明確に読み取れた値は区別。品目カテゴリに迷いがある場合は選択候補を表示。
- 読み取り画像に個人情報がある可能性を前提に、実データを検証スクリーンショットやログへ出さない。
- OCR・判定モデルをどう組み合わせても、UI側は成功/曖昧/失敗/部分成功の状態を持つ。

## 11. マイクロインタラクションとモーション設計

2025年のMaterial 3 Expressiveで重要なのは「全部を跳ねさせる」ことではなく、視認性・状態変化・操作反応の意味づけ。

例:

- タップ時: 押されたと分かる視覚変化を即時表示。保存処理が始まったことは別の状態で示す。
- シート表示: 操作元が理解できる速度と方向で現れる。複雑なバウンドは控えめ。
- タブ切替: 現在地が即理解でき、選択状態が一貫している。
- 入力エラー: 対象フィールドに説明を表示。大げさな揺れは必須ではない。
- 成功時: 少しの触覚や控えめなステータス通知。アニメーションだけでは知らせない。
- データ更新: 合計値の変化が追えるが、常時数字が回転し続けたり目立ちすぎない。

**減速動作/reduced motion**への対応を持ち、ユーザーがアニメーションを減らしているときは省略/短縮できる構成にする。描画コストの高いBlurや重いShadow、何段にも重なる透明レイヤを多用しない。

## 12. Material 3 Expressiveの採用ルール

採用できる点:

- 重要な操作を目立たせるタイポグラフィやコンポーネント変化。
- 状態の遷移とタッチ反応の自然さ。
- システムの設定・動的色との整合。
- Android標準のシート/メニュー/選択UIを尊重する。

避けたい点:

- 予算と支出を確認するだけの画面を派手にする。
- 色や形のバリエーションを増やしすぎて一貫性を失う。
- AndroidとiOSの画面を無理に完全一致させ、片方の慣習を壊す。
- OS準拠を名目にブランド・アクセシビリティの要件を無視する。

## 13. Expo UI / Native Tabs導入の技術判断

`@expo/ui`は2026年のExpoの重要な変化。ReactからAndroidのJetpack Compose、iOSのSwiftUIのネイティブコンポーネントを呼び出せる。ただし`Host`内の要素配置、RNとのデータや状態の橋渡し、対応API、各OSの見た目の差は調べる必要がある。

### 13.1 まず候補にする部品

- システムらしいButton / Switch / Picker / Slider / Menu / BottomSheet
- フォームのグループ、設定の一覧
- 標準タブ、各OSの戻る・モーダル挙動

### 13.2 簡単なComposeボタン例（Expo SDK 58の記法）

```tsx
import { Host, Button } from '@expo/ui/jetpack-compose';

export function SaveButton() {
  return (
    <Host matchContents>
      <Button onClick={() => { /* save handler */ }}>保存</Button>
    </Host>
  );
}
```

この例は使い方のイメージ。実際のpropsとButtonのテキスト子要素の互換性は、対象版のドキュメントと型定義で必ず確認。

### 13.3 Native Tabsの判断

- システム既定の触覚/余白/戻る/OSデザインとの整合を重視する場合はnative tabs。
- 既存のブランド専用ボトムナビで実現したい構成があるなら、カスタム/ヘッドレスタブも候補。
- Android側で5タブ超は別設計が必要。隠された機能の発見性と操作回数も評価。
- AI解析のような一時的行為をタブ化すべきか、中央追加ボタンのサブメニューに入れるべきか議論して決める。
- iOS版が存在するので、Androidだけの最適化でiOSの体験を壊さない。

### 13.4 Expo UIのドキュメント整合性に注意

`@expo/ui`のUniversal List文書では大規模データに`List.ForEach`が記載される一方、Expo Skillsの`expo-ui`紹介では、設定画面のようなグループ行向けで、大規模リストにはFlatList/FlashListを使うよう示唆している。Codexは両者の更新日を照合し、現行SDK・実装を調べた上で、1千/1万件の取引履歴を同じ条件で動かして判断すること。どちらかを事実確認なく絶対視しない。

## 14. Kotlin / Jetpack Composeを比較試作するときの正しい比較

Android専用開発ならJetpack Composeがもっとも直接的な実装の候補。テーマ、WindowInsets、LazyColumn、State、Navigation、Baseline ProfilesなどをOSのスタックで制御できる。

- `Scaffold`で画面を組み、下部ナビ・Snackbar・TopBarとのInsetを整理。
- `LazyColumn`には安定した`key`と必要に応じて`contentType`を用いる。
- 状態はUIに必要な単位に分け、再コンポーズを抑えるために測定する。
- 大きな集計をComposable内で毎回行わず、データ層で整理する。
- Android 12以降の動的カラーは採用の是非を選ぶ。ブランド色と選択肢を統合できるか検証する。
- Material 3 Expressive部品の安定APIと対象Composeライブラリの実バージョンを確認する。

例（概念例、プロジェクトに合わせてimport/テーマ/版を調整）:

```kotlin
@Composable
fun TransactionHistory(items: List<Transaction>, onOpen: (String) -> Unit) {
    LazyColumn {
        items(
            items = items,
            key = { it.id }
        ) { item ->
            ListItem(
                headlineContent = { Text(item.title) },
                supportingContent = { Text(item.category) },
                trailingContent = { Text(item.formattedAmount) },
                modifier = Modifier.clickable { onOpen(item.id) }
            )
        }
    }
}
```

注意: これは構造の例。Accessible semantics、コンテンツ領域の最小サイズ、差分更新、レスポンス状態は別途実装する。

## 15. Flutterを比較試作するときの正しい比較

FlutterはDartのWidgetツリーで統一したデザインシステムを組めるので、Android/iOSで独自の外観をほぼ揃えたいときに候補になる。ただし「iOS/Androidのネイティブ部品と同じ挙動に自動的になる」という意味ではない。

- `LayoutBuilder`等の利用可能幅から適応。OSや端末名だけで分岐しない。
- `SafeArea`を適切に使い、システムUIと重要要素を衝突させない。
- 多件数は`ListView.builder`等で遅延生成する。
- `const`化と小さいWidgetへの分割によって再構築範囲を明確に。
- 不必要な`saveLayer`、重いOpacity/Clip、Blurを減らす。
- Material系/Cupertino系のAPI構成が最新Flutterで変わっている場合があるため、現行公式文書を調べてコードを決める。
- 優位性をデザインの統一度と運用負荷で示し、既存Expoコードの書き直しコストも評価。

## 16. 低性能Android端末とデータ件数を想定した実測

### 16.1 デバイス条件

- ローエンド〜ミドルレンジのAndroid: CPU/メモリが制約になる場合を再現。
- 画面の大きいAndroid、ジェスチャーナビ、3ボタンナビ、ダークモード。
- iPhone端末（Expo版）、大文字設定、スクリーンリーダー。
- PC上エミュレータは便利だが、最終評価は実機で。

### 16.2 データ件数

- 0件: 空状態/導線/オフライン表示。
- 5件: ホームの短い履歴。
- 50件: 通常月のスクロール。
- 1,000件: 全期間履歴のスクロール/検索。
- 10,000件: 仮想化・フィルタ・メモリ負荷のストレス試験。

### 16.3 測る項目

- 初回表示までの時間（アプリのCold/Warm Start、画面初回描画）。
- 60/120Hzでのスクロール時のフレーム落ち・遅延。
- ボタンタップから視覚フィードバックまでの体感と計測。
- 日付/カテゴリ/キーボード切替時の引っ掛かり。
- 検索の1文字入力でリスト全体が無駄に再レンダリングされないか。
- 長い履歴を開いてもメモリが継続増大しないか。
- 画像表示にともなうメモリとキャッシュ。

デバッグ版だけでは真の性能を比較できない。Expo/RNとCompose/Flutterでリリース相当の最適化設定をそろえる。異なる端末での数値を単純に比較しない。

## 17. 見た目の比較だけではないA/B試作の仕様

### 同一条件

- 画面幅: 360dp程度の小型スマホ、393dp程度の標準幅、600dp以上の大画面。
- テキスト: 日本語、最大桁数の金額、長い店名、カテゴリ名、説明文。
- カラーテーマ: ライト/ダーク。
- 日付: 日本式表示と月/週/日切替。
- データ: 同じJSONのダミー取引。金額、カテゴリ、店舗名、予算を同じにする。
- 通信: ダミー/ローカルデータで画面性能を測り、通信待ちとの混同を避ける。

### 比較対象

A. 既存Expoで整えたUI（最小変更）
B. Expo + `@expo/ui` でネイティブ部品を追加
C. Kotlin + ComposeのAndroid参照実装
D. Flutterの比較実装（必要性があれば）

KotlinやFlutterを試す場合も、いきなり認証や銀行連携を作り直さず、デザインと操作が比較できる独立した画面を最初に用意する。

### 受け入れの目安

- 実機に表示されること。
- ステータスバー、ジェスチャー領域、キーボードが重ならないこと。
- フォント拡大時に主情報が読めること。
- すべての重要な押下可能要素にラベルと適切な領域があること。
- ダークテーマで文字・境界・警告が識別できること。
- 初期値/空/ローディング/失敗/復帰状態が全画面にあること。
- 戻る/キャンセル/保存済み判定が一貫していること。
- 取引の集計処理・保存データ・セキュリティをUI変更で壊さないこと。
- 数値目標（時間、FPS、メモリ）を設定する場合は、**ベースライン実測後に回帰防止目標を決める**こと。

## 18. 具体的な画面状態マトリクス

| 機能 | 通常 | 空 | 読込中 | 失敗 | 部分成功 | オフライン |
|---|---|---|---|---|---|---|
| ホーム | 指標/履歴/予算 | 取引追加導線 | 初期描画/プレースホルダ | 再試行+既知データ | 一部指標のみ | 最終ローカル情報の明示 |
| 履歴 | 日別行/絞り込み | 条件変更/追加 | 行・検索結果待ち | リトライ | 口座一部同期失敗 | ローカル履歴/同期待ち |
| 取引追加 | 入力と保存 | 初期状態 | 保存中 | エラーメッセージ | 一部項目未反映 | ローカル保存可否説明 |
| レシート | 解析・修正 | 画像未選択 | AI進捗/取消可否 | 解析/画像/通信エラー | 認識できた項目のみ | 未送信キュー/再試行 |
| 口座 | 残高/履歴 | 未登録導線 | 更新中 | 連携エラー | 一部口座のみ | 更新日時を明示 |

ここでの「部分成功」は**状態モデルの候補**。実際のバックエンドがサポートしないなら、見せかけの保存成功を実装しない。

## 19. AIエージェントの使い方：ツールを任せる順序

1. **資料の一次確認**: このパックのリンクから元資料を閲覧し、更新日時・バージョンを記録する。読めないサイトは理由を残す。
2. **既存実装監査**: package.json、Expo SDK、画面/コンポーネント、既存テスト、実機動作を確認。
3. **デザインの複数案**: Stitchは案出し、Figma/Figma Makeは構造・操作プロトタイプ、Codexは実装仕様と検証へ用いる。外部ツールは接続できる範囲で。
4. **Figmaへ戻す**: MCPでフレーム/Auto Layout/Variables/意味のあるレイヤー名を管理。Code Connectが使えるなら実装コンポーネントとの対応を設定。
5. **Expo公式Skills**: `expo-design-system` / `expo-native-ui` / `expo-ui` / `expo-router` / `expo-animation`を必要な課題ごとに参照。SDK一致のDocsを優先する。
6. **小さな実装**: ブランチを分け、1画面を改善し、型チェックと動作確認。
7. **スクリーンショット比較**: デザインと実機の差分を確認。見た目だけでなく操作の正確性もテスト。
8. **性能/アクセシビリティ**: 低性能Androidとフォント拡大/読み上げテスト。
9. **レビュー**: Astraで設計意図・品質・退行をレビュー。繰返し調整はSol。
10. **知識の永続化**: 最終トークン、部品API、状態仕様、採用しなかった技術と理由をファイルに残す。

## 21. 絶対に避けること

- 「DMMのように」という曖昧な形容詞だけで、無関係なコンポーネントを全面追加する。
- Android標準の操作を無視し、iOS流のナビゲーションをそのまま貼る（逆も同様）。
- 無意味なカード、グラデーション、Blur、Shadow、アニメーションを追加して「洗練」と呼ぶ。
- スクリーンショットや実機検証なしに視覚品質を断定する。
- 未アクセスの出典を読んだと偽る。
- SDK58向けAPIを古いExpoへそのまま導入する。
- Turtleの非公開Reactライブラリを公開済みとみなす。
- 単純な画面改修なのに認証/口座連携/レシートAI/集計アルゴリズムまで勝手に書き換える。
- 実機で測らず「Kotlinは常に速い」「Expoは必ず遅い」「Flutterは常に滑らか」など断言する。
- UX検証をしたと言いながら、タップ数や失敗時の状態を評価しない。

## 22. 目標をプロダクト固有に落とした5つの質問（Codex側で分析して答える）

1. ユーザーは最初の3秒でどの数値を見たいか。どのサブ情報を二次画面へ逃がせるか。
2. 「金額だけ記録」「商品ごとに記録」「レシート解析から一括記録」の3経路をどこまで共通化できるか。
3. 詳細履歴が増えても、一画面内の情報密度を保ちつつ操作の発見性をどう確保するか。
4. Material 3 Expressiveのうち操作を助ける要素は何か、ブランドの一貫性を壊す要素は何か。
5. Expoを維持したとき最も大きいUX上の制約は何か。Kotlin/Flutterへ移ると**測定可能な**改善があるか。
