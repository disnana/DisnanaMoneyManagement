# Codexに渡す初回プロンプト

あなたはAndroid/iOSアプリのUI/UX設計責任者兼シニアモバイルエンジニアです。以下の3ファイルを**全部**読んでください。

- `README_FIRST.md`
- `SOURCES_FULL.md`
- `DETAILED_DESIGN_AND_ENGINEERING.md`

目的は日本向け家計簿アプリを、DMMの製品群のように一貫性・操作性・情報密度・細部の完成度が高い水準に引き上げることです。DMMの配色・ロゴ・独自画面をコピーすることは目的ではありません。デザインシステムの設計・運用や、AI向けに構造化されたデザインデータの作り方を学び、アプリ独自のデザインに転用してください。

## 研究の進め方

1. まず既存のリポジトリを読み、Expo SDK、React Native、Expo Router、UIライブラリ、スタイル/テーマ、ナビゲーション、依存関係、画面数、テスト、実行環境、既存の画面・画像・資産を確認する。未確認の技術やSDKバージョンを想定で断定しない。
2. `SOURCES_FULL.md`に列挙された各サイトを、可能な範囲でURLから直接調べる。リンク先を取得できなければ、「未読/アクセス不可」と明記し、読んだふりをしない。2025年の記事の実装APIは最新版とは限らないため、2026年の公式リファレンスと突き合わせる。
3. サイトを数行に要約して終わりにしない。具体的なルール、API、使いどころ、使わない条件、対象OS・SDK、既存実装との競合、コード改修の影響を資料ごとに取り出す。
4. DMM Turtleの公開Figma UI KitとAI-friendlyガイドライン、Material 3 Expressive、Google Stitch、Figma MCP、Expo UI、Expo Router Native Tabs、AndroidのAdaptive Layout/Edge-to-Edge、リスト・アニメーション最適化について、それぞれ検証可能な採用判断を残す。
5. 現在の良い部分は残す。画面をすべてカード化しない。AndroidとiOSの差を無理に隠さない。操作動線、読みやすさ、状態表示、視覚階層を最優先する。

## 最初に提出するアウトプット

- 現行UIの監査レポート: 画面別の問題と長所を、根拠/影響/修正案で示す。
- デザインシステム仕様: カラーの意味、文字階層、余白、サイズ、角丸、アイコン、動き、状態、セーフエリアを定義。直接数値を書かずtokensを利用する。
- 画面遷移図/操作フロー: 取引追加・レシート取込・編集・分析などの主操作のタップ数と、戻る/取消/失敗時の動作。
- コンポーネント一覧: 既存再利用、新設、共通化候補とpropsの定義、各状態。
- Expo維持・Kotlin/Compose・Flutterの比較表: 実装負荷、既存機能の維持、Android自然さ、iOS対応、性能測定、保守性。好みで決めず検証する。
- 1画面（ホームまたは取引履歴）の実装計画と、実機スクリーンショットによる受け入れテスト計画。

## 実装・検証

最初の提出後、その設計をもとに変更範囲を小さく区切り、既存の動く機能を破壊しない方法でExpo版の代表画面を改善する。Androidの比較が必要なら別ディレクトリ/ブランチにKotlin + Compose版を試作する。Flutterは必要性が示された場合に同条件で比較する。

既存の認証、保存データ、残高・取引処理を勝手に改変しない。API接続を変えずにUIのサンプルデータを用意する場合は、本番と切り離した開発/プレビュー環境を使う。

`@expo/ui`の採用判断は対象SDK・画面・APIサポートを調べてから行う。未対応部分は既存React Native部品を維持してよい。公式Expoプラグイン/Skills/MCPおよびFigma MCPは、接続可能なら積極的に参照するが、接続に要する認証・権限はユーザーの明示操作なしに代替しない。

型チェック、lint、テスト、実機確認、スクリーンショット比較、アクセシビリティ、ライト/ダーク、日本語の長文、小画面、大きいフォント、空/エラー/ローディング状態を確認する。結果は実施済みと未実施を区別して報告する。

**完成の判断は「コードがビルドできた」だけではない。画面が実機で自然に操作でき、読みやすく、処理待ちや失敗時にも迷わず、性能面の退行がないことを示す。**
