# 画面と実装の対応

以下は設計案。金額の意味を統一してから、日常の照会、最後に新しい入力元を加える。各段階を独立して試せるようにする。

## 既存画面に組み込む部品

| 使う画面・既存の実装 | 変更案 | 必要な状態と操作 |
| --- | --- | --- |
| ホームの `HeroCard`、口座タブの `AccountSummaryRow`、`useCurrentBalances` | 今日時点・選択家計の純資産、現在の口座残高、カード未払いをそれぞれ名付ける。ホームで資産を隠したら内訳とそのアクセシブルな金額も隠す。口座名と残高をそろえ、全件合計を一覧の末尾に置く。 | 現行の表示・非表示設定を再利用。ゼロも負数も残す。折りたたんだ場合は「全7口座の合計」のように母集団を示す。カードの利用可能枠は資産に足さない。 |
| 取引タブの `MonthScreen`・`TxGroups`・`TxRow`、`/search` | 月と対象家計を冒頭で確認。日付を同じ日に繰り返さず、店名→支出入の符号と額→必要時のポイント・実支払の順で読めるようにする。タップで既存の編集へ。 | 月・家計・種別・検索条件・リスト位置を戻る操作で復元。小さい画面では店名と金額を上下に配置する。親指で押せる領域と文字の大きさは独立させる。 |
| 分析の `analytics/index` と `analytics/category`、`computeMonthMetrics` | 同一の寄与明細から円グラフ・カテゴリ行・詳細を作る。詳細では店名または振替元と、当該カテゴリへの寄与額を表示する。円以外に金額・割合のテキスト一覧を維持する。 | フィルタの対象は家計・月・支出入・カテゴリ。立替・回収は家計収支の対象外、振替は手数料だけ。詳細から元の取引編集に入れる。 |
| ＋から開く `add.tsx` と `TransactionForm` | 支出入力の中の「レシートから」に撮影・画像選択をまとめる。金額を手で打つ人は今と同じ入口、同じ保存操作を使う。カメラ拒否時も記録を続けられる。 | 撮影中、読取中、要確認、保存中、完了、失敗の各状態を区別。読取中に抜けても保存操作扱いにしない。再試行後に古い完了イベントを表示しない。 |
| 新設する読取確認画面 | 日付・店・合計を一画面目に置き、「合計のみ」「品目別」の切替をその下に置く。品目別では1行が商品名、カテゴリ、金額。選択行だけを編集し、原文と照合できる。 | 要確認は文字と項目名で表示。保存操作は「1,080円を記録」または「内訳3品・1,080円を記録」。端数・割引・税を含む差額も金額で示す。 |
| 設定→データ管理の `MonemyImport` と別枝の `CsvImport` | ファイル選択→取込先→プレビューの既存手順を使う。完全な再取込、同じ支払いかもしれない候補、新規を分ける。候補の比較だけで画像・手入力・銀行明細の出典を開く。 | 各行で含める／保留／関連付けを変更。確定前に追加件数と残高への影響を表示する。同じ額でも別会計の選択と解除を用意する。 |

ホームで口座を毎回展開すると今月の支出が下に押し出される。標準は先頭4件と全件合計を試し、長い一覧の操作は口座タブに渡す。既存の「ホーム・取引・＋・分析・口座」と、利用者が覚えた＋の位置は保つ。キャラクターは撮影の初回案内と困った時の手入力への案内に使う。残高行・品目行には名前と数字を置く場所を確保する。

## P0　数字を信頼できる状態にする

1. **分析の集計と詳細を一致させる。** `packages/core/src/utils/metrics.ts` の `addCashFlow` の判断を共有し、1取引がどの区分・カテゴリへ何円寄与するかを返す。現行取引は最大1成分。将来の品目別記録では1取引が複数成分を返す。月のキャッシュフローは既存月インデックスを使い、詳細行には元のIDと寄与額を渡す。詳細から編集する際は元の振替や決済全体を開く。[集計](../../packages/core/src/utils/metrics.ts)・[現行の詳細](../../apps/mobile/src/app/(tabs)/analytics/category.tsx)
2. **同じ買い物で数字を突き合わせる。** 架空の同月に自分の食費1,200円（200円分ポイント）、立替食費600円、振替10,000円・手数料110円を用意した。`main` の集計関数とカテゴリ詳細の絞り込み式を実行すると、月の支出1,310円、食費1,200円、手数料110円に対して、詳細は食費1,800円・手数料0円だった。修正後は1,200円と110円。元の買い物の実支払1,000円と食費1,200円の区別を保つ。立替の回収、カード支払い、事業と個人の切替も同じ試験に加える。[ポイント・手数料](../../packages/core/src/utils/format.ts)・[立替](../../packages/core/src/utils/advances.ts)
3. **資産用語と表示対象を決める。** 各口座の「今日時点の符号付き円残高」を既存の経路で一度だけ取得する。提案は、正残高の和を資産、負残高の絶対値の和を負債、その差を純資産とすること。カードの返金超過、マイナスの銀行残高、複数家計、連携デビット、将来日付の決済で検算する。外貨は現在の保存単位・参考円換算に従い、円換算済みの値に再度レートを掛けない。今後の「評価額」にはレート・基準日を付ける。[残高計算](../../packages/core/src/store/finance.ts)・[今日時点の残高](../../apps/mobile/src/lib/currentBalances.ts)
4. **照会の見やすさを検証する。** 架空の7口座で一覧の合計90,890円、カード未払い12,400円、差引78,490円を別々に質問する。これは口座合計と差引を検証する例であり、口座のうち1つがマイナスのため、正残高だけを合算する上記「資産」とは区別する。標準文字で最初の店名と金額が同時に見え、200%でも年月、長い日本語名、マイナス符号、合計の末尾が読めるかを確認する。

## P1　既存の取込と、手で直せる下書き

**CSV。** 銀行CSV試作の3形式を起点に、三井住友銀行と三井住友カードを異なる形式名として扱う。PayPay銀行は操作日時・取引順番号、楽天カードはe-NAVI利用明細など、既存パーサーが持つ出典と取込先の意味を維持する。現在の口座残高を開始残高に入力済みの人に昔の明細を足す場合は差分を先に見せる。異なるファイルの重複、取消・返金、文字コード、対象外行、0件、口座不一致を既存データの複製で検査する。3形式の取り込みは調査時点で別ブランチの実装。[試作の取込処理](https://github.com/disnana/DisnanaMoneyManagement/tree/2ce792d/packages/core/src/utils)・[mainのMonemy取込仕様](../monemy-import.md)

**レシート確認。** まず手で用意した架空の読取結果を使い、プロバイダーに依存しない確認・修正・取消画面をつくる。提案する `ReceiptDraft` は下書きID、出典、日付、店、合計、商品原文・行額・カテゴリ候補、ユーザー修正済み項目を持つ。各候補の出所を区別し、未取得は空欄のまま訂正可能にする。モードを行き来しても訂正値を保持。画面を閉じるときは下書き保持／破棄を選べる。画像の保管は独立した選択にし、画像・認証情報を分析ログへ出さない。

**会計上の単位。** 合計のみは既存の支出1件。品目別でも残高に効く支払いは1件で、各内訳を検索・編集・カテゴリ分析できるようにする。例として、食費780円と日用品420円、ポイント200円なら、家計の支出1,200円、カードへの請求1,000円、カテゴリへの寄与780円と420円。品目合計が1,199円なら1円差を確認画面に残し、「値引・税等の調整」「修正」「合計のみ」のいずれかを選ぶ。差額を商品へ黙って配らない。合計のみへ切り替えた際に採用するカテゴリも示す。

**保存と照合。** `Transaction` への追加候補は省略可能なカテゴリ内訳（安定した行ID・品名・カテゴリ・整数円の寄与額）と出典参照。税・ポイント・実支払いは既存フィールドと同じ意味にする。既存の `monemySource` は読める状態を保つ。画面からは一度のstore操作にまとめて、書込みが成功してから画面を閉じる。下書きの確定IDで二度押し・再試行を識別。複数明細や出典を別テーブルにする段階では、明細・出典・下書き確定を同一DBトランザクションに入れ、ブラウザの保存にも同じ原子性を持たせる。[データ型](../../packages/core/src/types/finance.ts)・[永続化](../../packages/core/src/store/financeDatabase.ts)・[バックアップ読込](../../packages/core/src/store/financeBackup.ts)

同一出典の同一行は取込済みとして扱う。異なる出典の「同じ支払い」候補は同一家計・対象口座・通貨・入出金の向きから絞り、利用日と計上日、ポイント控除後の実請求、店名を示して本人の判断を待つ。候補だけでは残高を変更しない。カードの月次引落は既存の銀行→カード振替に対応付け、個々の買い物と関連付けない。明細を紐づけた際は両方の出典を残し、一つの決済だけが計上される。誤照合の解除では選んだ取扱いをプレビューし、元の記録の状態と手修正を復元する。輸入元IDのない同日同額2件には自動確定を使わない。

## P2　読取・金融機関との接続を実測してから加える

- **Androidの読取。** 標準の画像選択またはカメラからアプリが選ばれた画像のみを受け取り、日本語用ML Kit Text Recognitionで文字・行・位置を抽出する小規模なネイティブ検証を行う。文字抽出と店舗・合計・品目の解釈は別の工程。日本語モデルの同梱版と初回ダウンロード版について、圏外初回の成否、AABサイズ差、処理時間を測る。まず端末内処理を検証し、クラウド解析を試す場合は送信先・対象画像・保持期間に同意してから送る。[ML Kit日本語認識](https://developers.google.com/ml-kit/vision/text-recognition/v2/android)・[Android写真選択](https://developer.android.com/training/data-storage/shared/photopicker)
- **Expoでの検証範囲。** Expo Goでも確認画面と手入力は模擬データで試せる。カスタムOCRモジュールは専用開発ビルドで試す。モジュールがない既存バイナリにOTAだけで読取ボタンを出さない。画像選択後のAndroidプロセス再生成、権限拒否、未取得モデル、斜めの感熱紙、長いレシート、同じ画像の再試行を試験する。失敗画面には「もう一度読み取る」「手入力を続ける」を出す。[Expo開発ビルド](https://docs.expo.dev/develop/development-builds/introduction/)・[Expoの画像選択とAndroidの復帰](https://docs.expo.dev/versions/latest/sdk/imagepicker/)
- **金融機関の自動取得。** 対応機関・正式な認可方式・契約・失効処理を先に確認する。手動口座はそのまま使え、利用者の同意を経て既存口座に接続する。同期の最終成功、明細が届いた日時、再認証、オフライン閲覧を区別する。APIで返る残高スナップショットと手入力の明細を両方残高に足さない。証券口座の実残高と時価評価の接続、資産推移は日付付き評価値を保持できてから扱う。

## 移行・性能・操作の受け入れ条件

| ケース | 検証方法と採用条件 |
| --- | --- |
| 既存データと巻き戻し | 旧形式の生JSON、v1バックアップ、移行済みSQLite、ブラウザ保存を複製して読込。書込み前後の件数、月の収支、各口座残高、請求残額を照合する。金額変化は確定した新規決済だけ。旧バージョンが内訳を欠落させる場合は形式を更新し、対応外の復元可否を表示して書込みを止める。OCRの機能スイッチを切っても確定済み内訳は読み出せるようにする。 |
| 重複・並行操作・中断 | 同一ファイル再送、画面連打、保存時の容量不足、編集中の口座変更、読取中のAndroid戻る、復帰後の完了通知を再現。一部だけ計上せず、やり直しても同じ購入は1回。手動入力とCSVの同額別件を保持できる。 |
| 描画・入力 | 同じ端末・同じ架空データ0／50／1,000／10,000件で、ホーム→取引→検索→編集→戻るを反復。リリース相当ビルドでタブを押してから最初の店名・額を描くまでの中央値とp95、フレーム超過、初回マウント行数を記録する。DB・OCR・描画を別区間にし、低下が再現した区間だけ最適化。月インデックスと書込み前検証を再利用し、必要時のみ仮想化する。[Androidの計測指標](https://developer.android.com/topic/performance/benchmarking/macrobenchmark-metrics)・[React NativeのFlatList](https://reactnative.dev/docs/flatlist) |
| 可読性・アクセシビリティ | 320・360・約412dp、600dp、文字100／140／200%、明暗、ソフトキーボード、3ボタン／ジェスチャーナビで確認。主要操作のタッチ領域48dp、通常本文コントラスト4.5:1を目標に、読み上げでは「店、支出1,200円、ポイント200円、実支払1,000円」を一度で把握できるかを試す。グラフとエラーは色に加えて文字で判別。両OSのアプリロック復帰を通してから採用する。[Androidでの検証根拠](revolut-android.md) |
| 導入判断 | まずP0を独立したPRで検証。P1はCSVプレビュー、読取確認、取引の内訳・照合の順に分割。P2は費用・権限・精度・遅延を調べる独立試験とする。符号・分類・残高が一致しない、既存データを戻せない、狭幅で保存できない場合はその段階で止める。 |
