# AIレシートの実装計画

## Go側の実装状況

検証用ブランチで、画像入力と結果の検証、Luna Standardアダプター、Scyllaのジョブ保存、既存ウォレットの仮確保・精算を実装した。受付の記録が途中で止まった場合の復旧では、ジョブを先に期限切れ扱いにし、ウォレットに同じ予約IDの取消を記録する。遅れて届いた予約は拒否し、すでに存在する未精算の仮確保は解放する。

ジョブと処理待ち画像のCQLは `apps/server/internal/receiptai/schema.cql`。リクエストを認証済み利用者とリクエストIDに結び付け、画像・料金の照合、受付、送信、結果保存、確定の各点を保護する。直接接続APIと各Goノードの処理を試験フラグで利用できる。受付時の料金版と上限は保存する。各試験ノードのモデル・推論設定は同じ値に揃え、試験ジョブの処理中の切り替えは避ける。

Scylla上の競合テストは、クレジットとレシートの両スキーマを入れた専用の検証用キースペースで `MANE_TEST_SCYLLA=1` を指定して実施する。通常のGoテストはメモリ上の競合、模擬HTTP、通信が途切れた場合の処理を検証する。

## 現在の構成と再利用

Androidの担当ノード接続・再割り当て・端末署名を再利用する。Go側の基点は `prototype/direct-node-sessions` の `0867f6b`。Goの `internal/androidauth` は署名付きの本人情報とクレジット残高を扱い、`internal/credits` は期限付きクレジットを優先する残高更新と、ScyllaDBのユーザー単位の条件付き更新を持つ。ウォレットの実装は `LOCAL_QUORUM` と `LOCAL_SERIAL` を使用している。Androidは受付IDを端末に保持し、ジョブ詳細を再表示する。サーバーの履歴一覧、取消、完了通知は今後の実装項目。

Workersは既存の認証入口と担当ノードの選定を担う。Androidは選定後にGoへ直接送信する。ノード変更後も、同じ利用者、クライアントのリクエストID、本文ハッシュを使って既存ジョブを取得できるようにする。異なる本文でのID再利用は409で返す。

## モデルと実行方式

| モード | Goからの呼び出し | 検証項目 |
| --- | --- | --- |
| 通常 | ResponsesのStandard。Goは受付後すぐに外部APIを実行 | キャッシュなしの単価、p50・p95、画像ごとの精度 |
| おまかせ | ResponsesのBackground、2hまたは8h枠 | 公開ベータの利用可否、完了・失敗・期限切れの実測 |
| 一括 | Batchの `/v1/responses`。グループごとに一意の `custom_id` | 24h枠、部分成功、結果とエラーの対応、ファイル削除 |

GPT-6 Lunaの `low` を第一候補にし、画像の高精度入力とStructured Outputsを組み合わせる。モデル、推論設定、プロンプトとスキーマのバージョンは受付時にスナップショットとして固定する。Fast、Flex、Geminiは初期対象から外し、Jevは必要性が実測で確認された補助用途を検討する。

提供された7画像のベンチマークでは、Luna lowの暫定正答率は81.0%、p95は8.271秒、キャッシュなしの推定原価は0.0003743 USD。Geminiは無料枠で503が出たため、有料環境の可用性比較には使わない。Backgroundの2hと8hは通常のモデル単価から30%・40%引き、Batchは50%引き。処理枠には部分失敗や期限切れがあり、ユーザー向けCR料金は収益・実測を基に別途決める。 [モデル仕様](https://developers.openai.com/api/docs/models/gpt-6-luna) · [Background](https://developers.openai.com/api/docs/guides/background) · [Batch](https://developers.openai.com/api/docs/guides/batch)

## 画像と解析結果

- 1ジョブに順序付きの画像グループを複数含める。1グループがAIへの1リクエスト。長いレシートの分割撮影は同じグループにし、無関係な書類はグループを分けられる。1グループに複数の書類が写るケースも評価する。
- Androidの撮影・選択画面では、明るい場所で反射・影を避け、文字と四隅が写るよう短く案内する。長い場合は途中を少し重ねて分けて撮り、送信前に画像と順序を見直せるようにする。送信直前に画像一覧と対象書類の例、最大CR、不鮮明で読み取れない、または書類が写っておらず対象外と判定された画像も精算対象になることを表示する。利用者は画像を1枚ずつ外す／差し替える／送信を取りやめることができ、内容を確認して送信する。画質判定で利用を制限する条件は評価してから決める。
- 送信前のプレビューでは、利用者が任意に余白を切り抜ける。切り抜き範囲と送信後の解像度をプレビューで確認でき、画像ごとに元の範囲へ戻せる。元の写真は変更せず、余白や背景を手動で除いた場合の通信量・原価の削減を評価する。同じ1枚のサイズを変えても枚数ベースのCR見積もりは変動しない。
- AndroidはUIスレッドの外で順次縮小デコードし、EXIF回転を反映して、元画像を維持したままメタデータを除去する。長辺1024、1536、2048、3072pxとJPEG品質を比較し、文字認識・ファイルサイズ・推論原価を測る。Goは形式、宣言値と実データ、バイト数・画素数、画像IDを検証する。
- 入力検証の試作はJSONに画像をBase64で載せる。公開APIの形式は、同じグループ情報を固定順のmultipartで送る方式と比較する。Base64の約33%の転送増と端末のメモリ負荷を計測し、端末署名が対象とする本文をノード切替時の再送で再現できることを確認する。
- `documents` に書類種別、抽出状態、検証結果、`source_image_ids` を持たせる案。明細付きレシートと合計だけの領収書、請求書、カード売上票、ATM明細、対象外、判定不能を区別する。読めない項目は `null`。明細が印字されていない領収書は合計だけで確認できるようにする。
- 金額は通貨ごとの最小単位の整数。税込・税抜、税率、値引き、支払額などの意味が確定した場合に照合する。差額や読み取り不足はレビュー理由として返し、印字値を保存する。カード番号欄は下4桁の文字列だけを許し、先頭が0でも保持する。画像内の文章はデータとして扱い、Webや外部ツールを呼び出さない。ユーザーの確認・編集後に家計簿へ登録する。

### Androidの撮影補助

- 撮影の候補はCameraXの `Preview` と `ImageCapture`。撮影前に水平・明るさ・影や反射・手ブレのヒントを出す場合は、低解像度のプレビューを `ImageAnalysis` で間引いて端末内で確認する。保存と送信は撮影した静止画のみ。長いレシートは全幅と文字の細さを保ち、必要なら利用者が少し重ねて分割撮影する。自動トリミングや台形補正は使わない。 [CameraXの画像解析](https://developer.android.com/media/camera/camerax/analyze)
- ML Kit Document Scannerは自動検出と補正を備えるが、補正した画像を返す撮影経路は今回採用しない。撮影補助としては、端末内のML Kit Text Recognition v2の日本語モデルを候補とする。小さな文字が読めるかの目安や撮り直し案内に使い、OCR結果だけで受付可否や課金を判断しない。 [Document Scanner](https://developers.google.com/ml-kit/vision/doc-scanner) · [Androidの日本語テキスト認識](https://developers.google.com/ml-kit/vision/text-recognition/v2/android)
- ギャラリーからの複数選択はAndroidのPhoto Pickerを優先候補にする。マネーちゃんのExpoアプリにはAndroidのローカルモジュール実績があるため、CameraXやML Kitが必要になったら同じ方式を比較する。最初は撮影時の短い案内と送信前プレビューで実測し、ライブ補助の効果と電池・低メモリ端末への負荷を評価してから依存を追加する。 [Android Photo Picker](https://developer.android.com/training/data-storage/shared/photo-picker) · [Expoローカルモジュール](https://docs.expo.dev/modules/get-started/)

## 永続化、復旧、課金

1. 受付では、見積もりID、料金バージョン、最大CRを照合する。画像を非公開の共有ストレージに耐久化し、ジョブとクレジット仮確保の回復手段が揃ってから202を返す。未確定の画像保存先は、利用可能な共有ストレージと実測サイズを比較して選ぶ。
2. 既存ウォレットのユーザー単位LWTで、仮確保・確定・解放と操作IDを原子的に記録する案。ジョブとウォレットが別パーティションなら、同じオーソリIDで再実行できる手順にし、途中状態を監視して復旧する。期限付きCRの優先順位と元の期限を保持し、期限後に解除した分を利用可能残高へ復活させない。
3. 未完了ジョブは時刻とシャードで区切った監視用の索引から取得する。状態本体を読んで処理可否を判断し、新しい監視予定を永続化してから古い索引を削除する。重複監視を許し、新規の外部送信と精算は条件付きで取得する。原本の照会に全件スキャンを使わない。
4. グループ単位で `SUBMITTING` と試行IDを記録して送信する。外部IDが保存された場合は別ノードでも照会できる。タイムアウトやノード停止で受付が不明な場合は `SUBMISSION_UNKNOWN` に保留し、外部で未受付と確認できるか、期限や復旧方針が決まるまで無条件の再送を避ける。精算前に結果を耐久化し、`SETTLING` から同じIDで再開する。
5. 取り込める結果が保存された画像、書類が写っていないなど対象外と判定できた画像、およびぼけや反射などの画質上の理由で読み取れないと正常に判定できた画像を精算する。通信・外部API・内部処理のエラーや未処理で、正常な判定結果を返せない画像分は解放する。画質の理由を特定できない判定不能の扱いは評価と相談で決める。故意かどうかを画像から推定しない。ファイルの欠落や形式不正は受付段階で弾く。1画像に複数書類があっても画像分は一度だけ精算する。上限超過分、失敗した呼び出し、内部再試行の原価は別に計測し、料金の試算に織り込む。料金改定後も受付時の見積もりを保持する。期限切れで解放した仮確保を、遅れて届いた結果のために再請求しない。
6. 解析が終わり精算が確定したら、サーバー側に送られた画像とアプリが作った一時コピーを削除する。履歴には解析結果を残し、端末の元の写真には手を加えない。終了や期限切れで取り残された画像も定期処理で削除する。Batch入出力ファイルの削除・失効も追跡する。OpenAI側の一時保存は自社ストレージの削除と別に評価する。画像・金融情報はログに記録しない。 [OpenAIのデータ管理](https://developers.openai.com/api/docs/guides/your-data)

送信ボタンを押す前に「対象外や不鮮明と判定された画像も、解析できた分はCRを消費します。送信前に画像をご確認ください」と表示する。結果画面では各画像の判定理由と確定したCRを確認できるようにする。

| ケース | CRの扱い |
| --- | --- |
| 店名と合計だけ読め、ユーザーが内容を確認して登録できる | 精算 |
| 書類が写っていない、または対応外の書類と判定した | 精算 |
| ぼけや反射で文字が読めないと判定した | 精算 |
| アップロード時点でファイルが壊れていて拒否された | 仮確保も精算も発生しない |
| 接続失敗や提供元・Goのエラーで判定を返せない | 該当画像分を解放 |
| 同じリクエストを再送した | 同じジョブを返し、追加で精算しない |

## 今後の検討　Jevの事前判定と上限見積もり

初期版はLuna単体とする。Jevの呼び出し、判定による振り分け、専用の課金は保留。送信前の見積もりに必要なLunaの原価試算と、最大CRの承認は初期版にも含める。以下は再検討時の資料。

### 採用条件

初期の通常解析はLuna単体。Jevは全画像で常時実行せず、利用者が希望した場合や、複数書類・繰り返し失敗などで本解析を省ける余地がある場合の候補とする。最初は検証画像で両方式の答えを比較し、Jevの結果で処理を止めない。TypeSafeは画像とBoxを試作向けとしているため、本番の拒否判定や自動切り抜きへの採用は精度検証後に判断する。 [TypeSafeの画像仕様](https://docs.typesafe.ai/images)

Jevには、ユーザーが選んだ範囲を維持した縦横比そのままのサムネイルを渡す。長辺512、768、1024pxを比較する。Jevは両辺280〜1568pxを要求するため、細長いレシートは短辺280pxまで余白で補い、画像を変形しない。対象領域の座標はプレビュー上の提案に使い、本人が確認して選んだ範囲を送る。曖昧な判定や複数領域は元の範囲でLunaへ進むか、利用者に確認する。 [TypeSafeの入力上限](https://docs.typesafe.ai/images)

経済性は「Jevの追加原価 ÷ 省けるLuna 1回分の原価」を超える割合で、安全に本解析を省けるかで判断する。例えばJevの画像・文章が合計1,024トークンなら、公式単価で約0.000043 USD。提供されたLuna Standard実測の0.0003743 USDでは損益分岐が約11.5%、同一条件のBatchでは約23.0%。1,024は仮定で、画像の実測値ではない。追加遅延、誤って書類を除く割合、確認や再解析の原価も一緒に比較する。 [Jev単価](https://docs.typesafe.ai/models) · [Luna単価](https://developers.openai.com/api/docs/models/gpt-6-luna)

### 原価、表示、精算

- Goで送信予定画像の縦横・枚数・detail・モデル・モード・スキーマ版を使って推定する。テキストには実際に送る指示、JSONスキーマ、OCRテキストを含める。Lunaの入力は `responses/input_tokens` と実行後のusageを検証用サンプルで突き合わせる。TypeSafeは画像トークンの事前計算式を公開していないので、画像寸法と実測のusageで補う。Lunaにも、公開資料で該当モデルの係数を確認できない場合は他モデルの係数を流用しない。見積もり前に本番画像を外部へ送らず、キャッシュ割引は事前の原価から除く。JPEG品質変更で転送バイト数が減っても、縦横とdetailが同じなら画像トークンが減るとは限らない。 [入力トークン数API](https://developers.openai.com/api/reference/resources/responses/subresources/input_tokens/methods/count) · [画像の課金](https://developers.openai.com/api/docs/guides/images-vision?api-mode=responses)
- Lunaの出力見積もりは推論トークンを含む。商品点数とグループ構成を分けて実績を集計し、予定原価は代表値、上限検討には原価のp95とサンプルのばらつきを使う。小標本ではp95を確定値とみなさず、安全余裕はまず運営の原価側に設定する。処理開始時にLunaの出力上限も設定する。 [推論トークンと出力上限](https://developers.openai.com/api/docs/guides/reasoning)
- 事前判定、Luna、両方の見積もりと最大CRを分けて記録する。利用者には課金条件、選択したモード、予定CR・最大CRを送信前に表示する。見積もりIDに画像・設定・有効期限を結び付け、送信時にGoで照合する。切り抜きを変えた場合は見積もりを更新する。API原価の変動は直接的な請求増額につなげず、正式なCR配分と端数処理は別途相談する。端数を導入する場合も浮動小数点を避け、段階・画像ごとに最低1 CRへ切り上げる方式と、ジョブ単位の合算方式で利用者負担を比較する。
- ジョブ受付時に両段階分の最大CRを1回だけ確保する。JevとLunaの結果・原価・外部IDはグループの処理段階として別々に記録するが、残高の確定は `SETTLING` の1回にまとめる。事前判定だけで終了した場合はその分、両段階を正常に提供した画像はその両方。誤判定、システム障害、内部再試行に追加CRを請求しない。Jevだけ失敗してLunaが成功した場合はLuna分のみ。上限超過分は運営が負担する。
- 対象外と確定して事前判定分を精算する有料オプションは、精度と価格に合意した後に有効化する。判定の確度だけで有効な書類を拒否しない。実画像での試験前に、Jev側の保存・削除条件も確認する。

## 通常解析のステージング試験

試験対象はAndroidからの通常解析。入力はJPEG/PNGのファイル選択。カメラ、アプリ内の切り抜き・縮小、おまかせ、一括は後続の実装項目。設定・受付・状態照会は以下の直接接続APIを使用し、すべて担当ノードの短命チャレンジと端末署名に結び付く。

| 方法 | パス | 用途 |
| --- | --- | --- |
| GET | `/v1/ai/receipt-config` | 試験価格、最大枚数、バイト数、画素数 |
| POST | `/v1/ai/receipt-jobs/{id}` | 画像、価格版、同意済み最大CRを受付。成功時は202 |
| GET | `/v1/ai/receipt-jobs/{id}` | ログイン中の所有者の進捗と結果 |

アップロードだけチャレンジの有効時間は60秒。サーバーは端末署名をチェックしてから本文を受け取り、署名対象の本文SHA-256を照合する。別ノードへの再送は同一ID・同一本文と価格版を使用する。Googleログインや残高照会のチャレンジは従来の5秒。

試験環境には既存のScyllaウォレットとAndroidの共有セッションを用意し、レシートの [CQL](../apps/server/internal/receiptai/schema.cql) を検証用キースペースに適用する。各Goノードで以下の変数を設定し、既存の `--check-config` を通してから試験ノードで起動する。鍵はサービスの環境ファイルに置く。

| 変数 | 試験で使用する値 |
| --- | --- |
| `MANE_RECEIPT_ENABLED` | `1` |
| `MANE_RECEIPT_OPENAI_API_KEY` | 試験用のOpenAI APIキー |
| `MANE_RECEIPT_PRICE_VERSION` | 同じ価格版を各ノードに設定する。例 `standard-test-v1` |
| `MANE_RECEIPT_CREDITS_PER_IMAGE` | 合意した試験用の整数値 |
| `MANE_ANDROID_SHARED_SESSIONS` | `1` |

Androidの検証ビルドでは `EXPO_PUBLIC_ANDROID_RECEIPT_ENABLED=true` を設定して作成する。手順は、少額の試験CRを付与し、画像を選択、上限を承認、結果確認、残高照合の順。各段階で同じジョブIDを使い、別ノードからの結果取得、画像の削除、失効済みCRの表示も確認する。画像やリクエストデータは実在の金融情報を含まないフィクスチャを使う。最初の接続は隔離キースペースで行い、稼働中の利用者データは使用しない。

新規受付は最大4画像・JSON 4 MiB以内。処理待ち画像をScyllaの専用テーブルに保管し、精算後に削除する。削除はCQL上の論理削除で、SSTableとバックアップからの消去は運用設定に依存する。ワークキューは8シャードを定期確認し、通常解析をノード当たり最大2件並行で外部送信する。本番の上限は実測後に決める。

実APIの応答に使用量があれば、画像枚数、応答時間、入力・キャッシュ・出力・推論トークン数をGoのログに記録する。画像、解析結果、利用者IDはこのログに含めない。担当ノードとCRの期限、今後記録される失効分はAndroidの設定から確認できる。旧実装で取り除いた失効分は復元できない。
