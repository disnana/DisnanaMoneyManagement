# 取引履歴の改修設計

対象は main の `daf9d53`。画面は「取引」タブの一覧。期間、家計グループ、種別を選び、金額の理由を確かめて編集する人を想定した。強い色を付ける基準は、金額の意味または操作の選択状態が変わる場合とする。

## 改修前に決めたこと

1. 「選択月と家計」→「その月の収支」→「種別を指定した明細」→「日付・取引」の順に読む。月集計の対象を明細の種別で変えない。立替・回収・振替手数料・ポイントの規則は core の計算値を用いる。
2. 上部では年月と隣月への移動を露出。表示範囲を変える家計グループは「全グループ」または選択名を表示する。右上に検索と次の表示方法（一覧／カレンダー）を置く。下部の「ホーム・取引・＋・分析・口座」は使い慣れた配置を引き継ぐ。
3. 一覧では月の収支を主見出しの額にする。収入と支出は矢印・日本語ラベル・金額を組にする。取引種別は共通の下線で現在地を示す。日付の区切りに余白と罫線を使い、店名・口座・金額の列は日をまたいでも同じ位置に置く。
4. 一件の行全体から編集できる。長押しメニュー、ポイントと実支払額、振替元・先、メモを保つ。日計は表示した取引の収支であり、振替元本は含まない。確定や削除、保存失敗の経路は既存の編集画面に集約する。
5. 一覧のスクロールは SectionList が所有する。日付と各取引を別セルにし、初期表示やフリングですべての取引をマウントしない。隣月のスワイプ予告には既存の上限を適用する。iOSの戻るジェスチャー領域、Androidの設定によるタッチ反応、モーダル、ロック、同期は既存実装を使う。

## 比較した配置

|案|最初に分かること|操作と不利な点|判断|
|---|---|---|---|
|A　月＋日記帳|対象月、収支、次に直近の利用内容。同じ左端を基準に読む|検索・カレンダーとも1タップ。上部をスクロールすると広く履歴を使える|履歴の代表案として実装|
|B　日付優先|履歴が最初から多く見える|月集計を開閉する操作が毎月発生。カード決済を含む月全体を把握しづらい|履歴専用ユーザーの比較候補|
|C　カレンダー優先|支出が集中した日を探しやすい|店舗を探すには日を選ぶ必要がある。小幅・大文字ではグリッドの密度も上がる|既存のカレンダーモードに残す|

## 実装の境界と受け入れ

|境界|仕様 / 確認の仕方|
|---|---|
|設計上の正本|既存の `usePalette`（OS別・明暗）の text / textSecondary / bg / fill / tint / income / danger を参照。今回の履歴の寸法と文字階層は `src/ui/historyStyles.ts` に置く。押下色を tint と通常背景の組み合わせで確認する。|
|月のページ|全画面に共通する `MonthScreen` の月スワイプ、結果の一度だけの反映、隣月の操作・読み上げ除外を使う。スクロールの所有権を一覧へ引き渡せるようにする。|
|月のヘッダー|対象月と家計・収支ごとの既存集計を表示。長い金額と大きな文字では統計を縦方向へ逃がし、主要金額を省略しない。年月ボタン・左右矢印は実タップ領域を確保する。|
|種別・空状態|すべて／支出／収入／振替は1タップ。選択状態を文字・下線・読み上げで示す。該当種別のみ0件なら解除、月に取引が無ければ記録または年月変更に進める。|
|明細|日付と候補取引IDをキーにする。行の高さは実際の文字・メモに従う。グループ順と同日内の表示順、再編集のID、月額と日計の母集団を機械検査する。|
|確認条件|隔離した架空データ 0/5/50/1000/10000 件、年月2026-11。5件は2件の同日支出、長い店名、200円分のポイント、給与、手数料付き振替を含む。360/標準/600dp以上、明暗、OSフォント拡大。|
|比較の単位|同じ月とデータを同じ端末上で表示・スクロール・編集・戻る。処理時間とフレーム数はビルド条件とセットで記録する。エミュレーター、ブラウザ、物理端末、利用者の試用を別々に記載する。|

このブランチでは Expo の1画面で効果を検証する。既存の Kotlin・Flutter 各試作には金融機能やOS対応範囲に差がある。比較対象と条件の詳細は `review-native.md`、Expo SDK 58 のライブラリ選定は `review-expo.md` に記録する。

### 製品固有の優先順位

最初に見せるのは、選択月を黒字／赤字のどちらで終えたかとその金額。対象の月・家計を見てから、収入と支出のどちらが主因か、気になる日と店名へ進める。資産全体と予算の判断はホームですでにできる。レシート解析の将来案は、手入力のレビュー・保存経路へ接続する構想までとした。OCR、商品認識、クレジット消費を実行するAPIはこのモバイル版に存在しない。[現行監査と遷移図](audit-and-flows.md)

Expressiveから採ったのは重要な金額の文字階層と、操作できる場所に意味を持たせた形。月送りと編集のOS動作を優先し、明細の出入りごとのアニメーションは設定しない。Expoで残る制約は高さが可変の長いリストの未測定領域とJS・ネイティブの境界。移植の判断には元の入出金規則・データ復元・OS別操作を揃えた状態で同じ作業が速くなることが必要になる。
